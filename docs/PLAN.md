## 1. 완료 (검증된 것)

### 모델 구동 — 계획서 "구현 방법"
- CatVTON을 **직접 구동**한다 (외부 API 미사용). Colab / Kaggle 양쪽 동작
- Python 3.9 venv 자동 구성 (`scripts/setup_env.py`) — repo가 요구하는 환경을 그대로 재현
- 구동까지 부딪힌 환경 문제 **9건**을 원인·해결책과 함께 문서화 → `docs/ENVIRONMENT.md`

| 항목 | 수치 |
|---|---|
| 환경 구성 (최초 1회) | 약 4분 |
| 모델 로딩 | 약 40초 (앱 시작 시 1회) |
| 추론 (기본값 DPM++ 8스텝) | T4 약 21초 / P100 29초 |
| 추론 (DDIM 30스텝, 벤치마크 기준) | T4 73초 / P100 103초 |

### 웹 UI — 계획서 "앱"
`app/gradio_app.py`. 사진 2장 업로드 + 옷 종류 선택 → 합성 결과.
Colab에서 공개 링크가 생성되어 팀원·교수님이 직접 조작 가능.

### 테스트와 측정 — 발표 자료용
`scripts/benchmark.py` + `scripts/make_report.py`로 45건 자동 실행 → `docs/TEST_RESULTS.md`

- **품질 시나리오 13건**: 인물 4명 × 옷 4벌, 상의/하의/원피스, 의도적 실패 케이스
- **속도/품질 32건**: 스케줄러 2종 × 스텝 4단계 × CFG on/off

### 속도 최적화 — "기술적 기여"로 발표할 부분
P100 기준 실측. 실제 쇼핑몰 상품 3벌로 검증 완료.

| 설정 | 시간 | 배속 | 옷 재현 |
|---|---|---|---|
| DDIM 30 + CFG on (원본 설정) | 103초 | 1.0x | 기준 |
| **DPM++ 8 + CFG on (현재 기본값)** | **29초** | **3.5x** | **유지됨** |
| DPM++ 4 + CFG on | 15.7초 | 6.6x | 사진 프린트가 쪼그라듦 |
| DPM++ 8 + CFG off | 16.2초 | 6.4x | **사진 프린트 옷 붕괴** |
| DPM++ 4 + CFG off | 9.3초 | 11.1x | **사진 프린트 옷 붕괴** |

**샘플러 교체(DDIM→DPM++)가 안전한 가속이고, CFG 끄기는 아니다.**
DDIM은 스텝을 줄이면 무너지지만(4스텝 SSIM 0.895) DPM++는 8스텝에서 유지된다.
반면 CFG를 끄면 시간은 정확히 절반이 되지만 옷 재현이 깨진다 — 무지 바지는 멀쩡하고
큰 글자 프린트는 흐려지는 정도인데, **사진 프린트 티셔츠는 알아볼 수 없게 뭉개졌다.**

#### 스텝 수를 더 줄일 수 있나 (실측)
20초 미만을 목표로 5·6스텝까지 내려봤다. P100 기준.

| 스텝 | P100 | T4 환산 | 옷 영역 SSIM (티셔츠) | 사진 프린트 재현 |
|---|---|---|---|---|
| 30 | 102.8초 | 73초 | 1.000 | 기준 |
| **8** | **29.1초** | **약 21초** | **0.953** | **유지됨** |
| 6 | 22.5초 | 약 16초 | 0.922 | **프린트 주제가 사라짐** |
| 5 | 19.1초 | 약 14초 | 0.859 | 사라짐 |
| 4 | 15.8초 | 약 11초 | 0.820 | 사라짐 |

무지 바지와 큰 글자 프린트는 4스텝에서도 쓸 만하지만, **사진 프린트 티셔츠는
6스텝에서 오랑우탄 그림이 통째로 사라지고 말풍선만 남는다.** 8스텝이 하한선이다.
→ 스텝을 줄이는 방식으로는 20초 미만을 못 맞춘다. 품질을 유지한 채 줄이려면
샘플링 스텝이 아니라 **스텝당 비용**(attention 구현, channels_last, torch.compile)을
건드려야 한다.

※ T4 환산은 이전 측정에서 얻은 비율(T4 ≈ P100 × 0.71)로 계산한 값이며 직접 재지 않았다.

#### SSIM의 한계 (발표에서 말할 것)
붕괴한 티셔츠의 SSIM은 0.950으로, 멀쩡한 맨투맨(0.953)과 사실상 같았다.
**인물과 배경이 화면의 대부분이라 옷이 망가져도 SSIM이 거의 안 움직인다.**

그래서 AutoMasker가 만든 **옷 마스크 안쪽 픽셀만** 재도록 바꿨다. 같은 이미지들을
두 지표로 재면 차이가 뚜렷하다 (티셔츠, 30스텝 대비):

| 스텝 | 전체 SSIM | 옷 영역 SSIM |
|---|---|---|
| 8 | 0.990 | 0.953 |
| 6 | 0.982 | 0.922 |
| 5 | 0.969 | 0.859 |
| 4 | 0.961 | 0.820 |

전체 SSIM은 0.99~0.96 사이에서만 움직여 판단 근거가 안 되는데,
옷 영역 SSIM은 0.95~0.82로 벌어져 눈으로 본 열화와 방향이 맞는다.
다만 이것도 완벽하지 않다 — 맨투맨은 4스텝에서 옷 SSIM이 0.764까지 떨어지지만
글자는 여전히 읽힌다. **최종 판단은 눈으로 한다.**

### 사이즈 파트 — 계획서 "세부 계획 2·4"
`app/body_profile.py` + `app/size_fit.py`. 사용자가 자기 치수를 입력하면
여유분을 계산해 S/M/L을 추천한다.

- **둘레 ↔ 단면 변환**: 사용자는 "가슴둘레 96"으로 알고 치수표는 "가슴단면 52"로 적혀 있다
- 아는 항목만 입력해도 동작, 빠진 항목은 판정에서 제외했다고 알림
- 단위 오타(96 → 9.6) 감지
- 단위 테스트 **49건** 통과 (GPU·mediapipe 없이 로컬 실행 가능)

## 2. 남은 작업 (우선순위 순)

### A. 합성과 사이즈 추천을 연결 — **가장 큰 구멍**
지금은 두 기능이 **따로 논다**. 사진 합성은 사이즈를 모르고, 사이즈 추천은 그림에 반영되지 않는다.
계획서 세부계획 3번의 *"여유분 값으로 실루엣 폭 조절"* 이 두 파트를 잇는 다리인데 미구현이다.

발표에서 "사이즈를 반영한 가상 피팅"이라고 말하려면 이게 있어야 한다. 접근 후보:
1. 사이즈별로 옷 이미지를 여유분 비율만큼 가로 스케일 조정 후 합성 (구현 쉬움, 물리적 정확도 낮음)
2. 마스크를 여유분만큼 넓혀서 합성 (실루엣이 실제로 넓어짐)
3. S/M/L 각각 합성해 나란히 비교 (가장 단순하고 시연 효과는 확실)

→ **3번으로 시작해 1번을 얹는 것을 권함.** 3번만으로도 "사이즈별로 이렇게 달라진다"를 보여줄 수 있다.

### B. 옷 치수표 데이터 확보
현재 `data/size_charts/`에 예시 2개뿐이다. 실제 쇼핑몰 상품의 치수표를 옷 이미지와 짝지어
최소 5~10벌은 모아야 데모가 성립한다. **수작업이 필요하고 생각보다 시간이 든다.**

### C. 실제 사진 테스트
지금 테스트는 전부 CatVTON 데모 이미지(스튜디오 촬영, 정면 정자세)다.
계획서 "우려되는 점"에 적은 **측면·팔 겹침·특이 포즈**는 미검증 상태다.
팀원 사진으로 돌려 실패 케이스를 수집해야 한다.

### D. 여유분 기준값 검증
`size_fit.FIT_BANDS`의 타이트/레귤러/루즈 구간은 일반적인 쇼핑몰 가이드를 참고한 값이지
측정으로 얻은 값이 아니다. 실제 옷 몇 벌을 입어보고 "이 여유분일 때 이런 핏"을 대조하면
근거가 생긴다.

### E. 품질 평가 보강
SSIM은 "베이스라인과 같은 그림인가"만 잰다. 사람 5~10명 A/B 설문 하나만 있어도
"가속해도 품질이 유지된다"는 주장이 방어된다.

### F. 앱 UI + 추론 서버 분리
계획서의 모바일 앱 단계. Gradio로 기능이 검증된 뒤에 착수.

## 3. 검증 안 된 것 (정직하게)

- **Gradio UI에 사이즈 입력란을 붙인 뒤 실제로 띄워보지 않았다.** 로직만 테스트됨
- `app/body_measure.py`(사진 기반 치수 추정)는 **절대 정확도를 신뢰할 수 없다.**
  보정계수가 문헌 어림값이고 캘리브레이션 데이터가 없다.
  사용자 직접 입력 방식으로 전환했으므로 지금은 보조 기능으로만 남겨둔다
- 측면·팔 겹침 등 어려운 포즈에서의 합성 품질
